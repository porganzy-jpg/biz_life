## 2. 구조 — 격자·원점·방향 규약

- **원점 (0,0,0) = 해저 바닥에 박힌 앵커 기둥 발의 중심.** Blender +Z 위.
- **유리 껍질** = 중심 (0,0,15), 반지름 13의 구. 바닥 z=2, 꼭대기 z=28. 돔은 해저에서 2m 떠 있고 기둥이 그것을 꿴다.
- **기존 6m 격자 유지.** 기둥 셀을 중심에 두고 이웃 여섯 칸이 거리 6.0m·60° 간격. 방 셀 = **맞변 6.0m 정육각 프리즘**(= 기존 한 칸), 벽 높이 **2.6m**(기존 규약), 슬래브 0.3m.
- **층 3개**, 층간 4.4m: L0 z=7.0 / L1 z=11.4 / L2 z=15.8. 같은 슬롯을 쓰는 방은 8.8m 이상 떨어뜨려 45°에서 서로 가리지 않게 배치했다.

- **벽 제거 규칙(B6)**: 6면 중 `cos(면각 − 225°) > 0.1`인 면을 없앤다 → 180°·240°·300° 벽이 빠지고 0°·60°·120°만 남는다. 벽이 없어도 육각이 읽히도록 **모서리 기둥 6 + 상단 림보 6**은 항상 세웠다. 기둥을 향한 안쪽 벽에는 문(문설주 2 + 상인방)을 뚫고, 기둥에서 셀까지 짧은 연결관(r=0.95)을 놓았다.

### 사선 절단 (이 태스크의 핵심)
평면 단면이 아니라 **구를 기울어진 평면으로 잘랐다.** 껍질 패널을 남기는 조건:
```
dot(u, VXY) < 0.62 − 0.45 · u.z        (u = 패널 법선, VXY = 수평 시선 방향)
```
법선이 `VXY + 0.45·Z` 인 평면 = **수평에서 24° 기운 사선**. 결과:
- 카메라를 정면으로 보는 허리께 유리는 사라져 **내부가 직접 보이고**,
- **꼭대기 유리는 남아** 위에서 유리 너머로 방을 내려다보게 되며(= 투과),
- **아래앞쪽 유리도 남아** 가장 낮은 방이 유리 뒤로 비친다.

절단 평면 ∩ 구 = 반지름 10.7m의 기울어진 원. 이 자리에 밝은 구조 칼라(`cutrim`, 72분할)를 둘러 "잘린 면"이 화면에서 읽히게 했다.

## 4. GLB — 규약과 용량

- **파일**: `static/models/scenes/dome_core.glb` — **1,500 KB (1,536,712 bytes)**, 메시 2개(`dome_core_body` 단색 / `dome_core_tex` CC0 텍스처) + 유리 3장(`keep_shell_glass`, `..._warm`, `..._rim`) + 마커 1.
- **원점 (0,0,0) = 해저 바닥의 앵커 기둥 발 중심.** 실측 bbox(Blender): x −13.21~12.99 / y −13.21~12.99 / z **−0.30~28.59**. 즉 **지형에 놓을 때 `position.y = 해저고도`만 맞추면 기둥 발이 바닥에 붙는다.**
- **축 변환**: `export_yup=True`로 내보냈다. **Three/glTF x = Blender x, y = Blender z, z = −Blender y.**
- **6m 격자**: 방 8칸의 중심은 전부 XY 원점에서 거리 6.0m, 60° 간격(0/60/120/180/240/300°). 층 z = 7.0 / 11.4 / 15.8.
- **마커** `marker_airlock_exit` — glTF 좌표 **(−1.10, 0.00, +9.00)**. 사다리 발치, 주민이 해저에 내려서는 자리.
- **유리 3장은 join에서 분리해 뒀다**(`keep_` 접두사). 알파 블렌드라 Three에서 `material.transparent = true`를 강제해야 할 수 있다(S2와 같은 이슈). 셰이더를 바꿀 거면 `DomeGlass` / `DomeGlassWarm` / `DomeGlassRim` 세 재질 이름으로 잡으면 된다.
- **조명 포함**(KHR_lights_punctual): 방 등불 8 + `L_beacon` + `L_airlock_out`. Three에서 과하면 0.3배 권장.
- **저폴리 모드**: `glb` 모드에서만 `LOW=True`가 켜진다 — 화분·덩굴 구체 분할 축소, 온실 화분 16→7, 서가 책 9→4, 사다리 26→10칸, 껍질 15×30→10×20, 절단 칼라 72→28분할, 통조림 더미 4→2. **렌더 3장은 항상 풀 디테일이고 GLB만 가볍다.** 이 차이를 여기 명시한다.

**정직한 기록**: 최초 내보내기는 **2,505 KB로 B8(1.5MB)을 넘겼다.** 텍스처가 아니라 지오메트리가 원인이었다(내장 이미지 7 KB, 본체 78,540 verts). 세 단계로 줄였다 — ① 중복 텍스처·재질 병합(`dedupe_assets`) ② LOW 모드 LOD ③ LOW 추가 트리밍. 2,505 → 1,641 → 1,500 KB. 여유가 거의 없으므로 **소품을 더 붙이려면 껍질 분할부터 낮춰야 한다.**

## 5. 자가 평가 — 직군 교본 03 §5 다섯 문항

**1) 주색 하나와 등불 하나가 보이는가?**
방 단위로는 **예** — 8칸 전부 등불 하나(점광 + 발광 전구)뿐이고 그 색이 방의 주색이다.
화면 단위로는 **의도적으로 둘**: 난색(안)과 한색(밖). 이건 B1 위반이 아니라 D1의 요구다.
다만 태스크의 "방마다 다른 등불색"과 D1의 "세 번째 주색 금지"가 충돌해서 **색상환이 아니라 같은 난색 대역 안의 색온도 차이로만** 구분했다(작업장 `#FF6E1E` ~ 온실 `#FFB63F`). 초록·청록 등불은 쓰지 않았다. **이 해석을 D1 우선으로 기록한다** — 지금 보면 방 구분이 약한 편이고, 실제로 PM의 후속 지시(§9)에서 D1이 "방마다 고유 색상"으로 개정됐다.

**2) 초록이 자란 자리가 있고, 사람이 오늘 밤 자는 흔적이 있는가?**
**예.** 초록은 온실(재배단 3 + 화분 16, 시드 난수 산포)·거주·라운지·목욕탕·도서실의 화분과 덩굴에 있다. 물속이라 야생 초록이 자랄 자리가 없으니 **초록은 전부 사람이 기른 것**이다 — 이 세계에서 B2의 "초록 = 생명"이 더 세게 읽힌다.
자는 흔적: 거주에 침낭 3 + 베개 + 빨래줄 + 벽 쪽지 3 + 컵 둘 놓인 낮은 탁자. 에어락엔 잠수복 5벌과 채집망의 유물 3개, 목욕탕엔 수건 4장과 오르는 김. **빈 바닥 없음**(방당 소품 10~20개, B4).

**3) 안/밖 중 어디인지 밝기만으로 알 수 있는가?**
**예.** 세 컷 모두 어두운 쪽 봉우리가 79~92%이고 돔 안이 화면에서 제일 밝다. 색까지 갈라 뒀다.

**4) 격자처럼 놓인 소품이 있는가?**
인공 구조(유리 격자·서가·재배단·잠수복 걸이·진열대·사다리)는 격자가 맞다 — B5의 "사람이 만든 것". 자연물(화분 위치·덩굴·관벌레·바위·부유물·발광 생물)은 전부 시드 난수 산포다.

**5) 용량·격자 원점·회귀 diff가 기준 안인가?**
격자 원점 ○(§4 실측). 회귀 ○(기존 도구 5개 `git diff` 비어 있음, 기존 `art_raw/iso`·`static/models/rooms` 무변경). 용량 ○(1,500 KB) — 단 §4의 초과 이력과 LOW 모드 차이를 기록했다.

## 7. 수정 이력 — 렌더를 Read로 직접 보고 고친 것

| 차 | 무엇이 잘못됐나 → 무엇을 고쳤나 |
|---|---|
| **1** | **우주로 읽혔다.** 순검정 배경 + 흰 사각형 부유물 = 별, 대형 생물의 판때기 지느러미 = 인공위성. → ① 시선에 수직인 **물기둥 그라디언트 배경판**(위 잔광 → 아래 칠흑) ② EEVEE 월드 볼류메트릭 안개 ③ 부유물을 1/5로 줄이고 1/3 크기로 ④ 지느러미를 납작한 타원체 열로 바꿔 유선형 실루엣으로 |
| **2** | 화면 전체가 창백한 청록 한 색. 돔 안이 바깥보다 밝지 않아 D1이 죽었다. 해저 바위마다 흰 Freestyle 윤곽이 낙서처럼. → 배경 그라디언트 대폭 암전, 방 등불 2.5배, 해저 재질 암전, `NOLINE` 컬렉션 도입 |
| **3** | (PM 중간 피드백과 같은 진단) 물이 여전히 밝고 올리브/카키 한 색으로 수렴, 해저가 광원 없이 밝다. → **전 볼륨을 균일하게 들어올리던 SUN을 0.85→0.11로 끄고**, 한색 반사는 감쇠가 있는 AREA 하나로. 안개 산란색을 청록으로, 등불을 더 주황으로 밀어 두 색을 갈랐다. 해저 대지 반지름 24→17m로 줄이고 가장자리를 −11m로 떨어뜨려 하드 엣지 제거 |

| **5** | 온실 등불이 하얗게 날아가 난색 대역을 벗어남 → 6200→4300W, `#FFC055`→`#FFB63F` |
| **6** | **화면 오른쪽 축 부호가 뒤집혀 있었다**(`sr` 양수가 화면 왼쪽). 구도는 우연히 맞았지만 코드가 거짓말을 하고 있었다 → `RIGHT`를 바로잡고 `UP = V×RIGHT`로 재정의, 호출부의 `sr` 부호를 뒤집어 구도는 유지 |

## 8. 미완 · 리스크 (정직한 부분)

1. **잠수복이 없다.** `dome_airlock.png`의 두 인물은 기존 역할 GLB(`scout.glb`, `engineer.glb`)를 **있는 그대로** 놓은 것이다. 헬멧·산소통·무게추가 없어 지금은 "해저를 맨몸으로 걷는 사람"으로 보인다. 캐릭터 에이전트에게 요청함(§9-1). DECISIONS 2026-09-22의 "주민은 무게추로 해저를 걷는다"가 화면에 아직 없다.
2. **GLB 용량 여유가 105 KB뿐이다**(1,500/1,536 KB). 소품을 더 붙이려면 껍질 분할(현재 LOW 10×20)이나 CC0 소품 수를 먼저 줄여야 한다.
3. **렌더가 느리다.** EEVEE 볼류메트릭 때문에 hero 4분 / depth 9분. 반복 수정 비용이 크다. 안개를 끄면 2배 빨라지지만 "물속"이 사라진다.
4. **부유물이 여전히 별처럼 보이는 구간이 있다.** 특히 `dome_depth.png`의 성긴 구역. 진짜 해결책은 화면에 늘 스케일 기준(생물·구조물)을 두는 것이고, 지금은 대형 생물 2마리와 해파리로 버티고 있다.
5. **유리의 알파 정렬.** EEVEE 알파 블렌드라 겹치는 유리 패널의 정렬이 완벽하지 않다. 정지화에서는 안 보이지만 실시간에서는 다시 볼 것.
6. **볼류메트릭 설정이 버전 의존적이다.** `scene.eevee.volumetric_*`를 try/except로 감쌌다. 다른 Blender 버전에서는 안개 없이 렌더될 수 있고 그러면 "물"이 약해진다.
7. **돔 꼭대기 캡이 여전히 화면에서 두 번째로 밝은 점**이다. 방의 등불이 주인공이어야 하므로 한 단계 더 낮추는 게 맞다.

### AI 공개 관리표(07 §6) — **갱신 불필요**
S3-B 산출물 전량이 Blender 절차 생성 + CC0(Kenney Survival Kit)이다. 생성 AI 이미지 0장, Pollinations 호출 0회. 새로 공개할 항목 없음.

## 9. 다른 직군에게

### 9-1. 캐릭터 에이전트 (S3-D)
- **잠수복 주민이 필요하다.** `dome_airlock.png`가 지금 그 구멍을 그대로 보여 준다. 최소 요건: 구형 헬멧(빛 반사면 1) + 등 뒤 탱크 + 발목 무게추. 실루엣만 바뀌어도 이 컷이 완성된다.
- 배치 규약: 해저 바닥 = **z 0**, 사다리 발치 마커 `marker_airlock_exit` = glTF (−1.10, 0.00, +9.00). 발 위치 원점·높이 1.7m 정규화는 기존 규약 그대로면 `iso.prop()`으로 바로 얹힌다.
- 대형 해양 파충류: 지금은 내 절차 실루엣(구체 열)이다. **원거리 배경 레이어 전용**이니, 실제 모델이 나오면 근거리용으로 쓰고 내 실루엣은 먼 층으로 남기면 된다.

### 9-2. 개발 에이전트
- `static/models/scenes/dome_core.glb` — 원점·축·마커·재질명은 §4. **아직 어떤 화면에도 붙이지 않았다**(태스크가 시스템 연결 금지).
- 유리 3메시는 `transparent=true` 강제가 필요할 수 있다(S2 파사드와 같은 이슈).

### 9-3. 사운드 에이전트 (S3-E)
- 이 세 장이 잡은 공간 스케일: 돔 지름 26m, 방 6m, 해저에서 꼭대기까지 28m. **에어락은 돔 바닥에서 해저까지 3m 관 + 사다리**다 — 물 들어오는 소리·사다리 금속음·해치 여닫힘이 그 길이 안에서 일어난다.
- 바깥을 비추는 빛은 등 하나뿐이다. 그 바깥의 정적이 이 게임의 "밖"이다.

### 9-4. PM에게 — 후속 지시(정면 평면 단면) 관련
- 이번 산출물은 **바깥 원정 시점 자산**으로 살아 있다. `dome_core.glb`는 그대로 쓸 수 있고, `dome_hero.png`·`dome_depth.png`는 원정 화면의 룩 기준이 된다.
- 다만 **정면 단면 화면에서는 돔의 내부 배치(육각 8칸)와 정면 단면의 방 배치가 서로 달라진다.** 같은 거점이 두 시점에서 다르게 보이면 플레이어가 혼란스러우므로, 정면 단면 쪽을 정본으로 잡고 원정 시점의 돔 내부는 **껍질과 불빛만** 보이게 정리하는 편이 안전하다. S4에서 그 방향으로 간다.
- `docs/TASKS.md`에 남길 요청: **없음**(내 소유 영역 안에서 끝냈다).
