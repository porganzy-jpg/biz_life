## 4. 교본 원칙 적용
- **D1 규칙은 적게, 조합은 많게** — 관문을 점수에서 떼어 "행동(관문) × 두께(점수)" 두 축의 곱으로 만들었다. 생물 11 × 역할 8 친화표가 조합을 만든다.
- **D2 모든 숫자는 화면의 무엇으로** — 판정의 `parts`·관문 `ko`·행동 `cost_ko`·`blocked` 를 서버가 문장으로 내려 화면이 계산하지 않는다. 선반은 숫자가 아니라 물건이다(E1).
- **D4 실패는 서사** — 상실 보호 2단, 관문 실패도 금에서 멈출 수 있음. 「돌려주기」는 도감 칸이 빈 채로 남는다.
- **D5 첫 3분** — 복구 코드는 탭을 하나도 늘리지 않는다(물어볼 때만). 첫날 세 칸이 스캔 없이도 된다. 첫 스캔부터 선반에 물건이 놓인다.
- **D6 결정성** — 판정에 난수 없음. 뽑기·세기는 `uid|day|raid|목적` 시드, 등급별로 시드 목적을 갈랐다.
- **D7 데이터가 규칙을 든다** — 수치는 `data/balance/*.json`, 방 수치는 economy, 글은 rooms.json/creatures.json. 코드 상수는 폴백.
- **공통 §3-6 더 단순한 쪽** — 홀을 칸에 짓는 방으로 만들지 않았다(이미 화면에 있는 척추).
- **이탈**: economy 의 배치 인원 비례 생산·전력 공급 모델은 넣지 않았다(이유: 새 방주 생산 0 → 첫 3분 붕괴 위험, TASKS 요청함에 기록).

## 5. 자가 검수 (02_DEV §5)
1. 새 숫자가 화면의 무엇으로 보이나? — 등급은 구역 이름·깊이 띠, 선반은 소품 그림, 관문은 「준비됐다/아직이다」 문장과 행동 버튼. 다만 그리는 일은 화면 담당 몫(계약 회신 남김).
2. 첫 3분 탭 수가 늘었나? — 아니다. 오히려 첫 증축이 스캔 없이 가능해졌다.
3. 같은 입력 같은 결과? — 판정 무난수, 뽑기 시드. 복구 코드 발급만 `SystemRandom`(맞히기 어려워야 하므로 의도).
4. 720px 손가락 조작? — 서버 작업이라 해당 없음. 행동은 버튼 하나(`/api/ark/act`)로 끝나게 설계.
5. 회귀 7항목 로그? — §3-3, 전부 OK.

## 6. 미완·리스크
- **화면 미연결**: 관문 행동 버튼·레벨업·선반 그림·복구 코드 UI 는 화면 담당이 `base.js` 에서 붙인다. `/base` 에 지금 `openAccount is not defined` 콘솔 에러 1건(화면 담당 작업 중으로 보여 손대지 않음).
- `static/base.js` 의 ZONES 해구 문턱 150→180 한 줄은 내가 S10-C 앞부분에 고친 것으로 아직 작업 트리에만 있다. 화면 담당 커밋에 함께 들어가야 서버와 맞는다.
- 신규 위협 가중치·「숨의 손」 각인·배치 비례 생산·전력 모델은 요청함으로 넘김(임시값 B7).
- 복구 시도 제한은 메모리에만 있어 서버 재시작 시 풀린다(속도 제한으로는 충분하다고 판단).
- 덮개는 「사람을 옮긴 횟수」만 센다. 귀환(recall)·조명·전원 토글은 움직임으로 치지 않는다.
- 선반 소품의 폭(1·2칸)은 `props_meta.json` 에서 읽는다(배경 소유 파일, 읽기만).
- 테스트용 방주(uid `s10c_*`·`s10reg_*`)가 DB 에 남아 있다.
