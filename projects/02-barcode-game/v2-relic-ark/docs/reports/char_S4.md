## 2. A안 / B안 — 무엇이 다른가

**두 안은 같은 렌더에서 나왔다.** 다른 것은 후처리뿐이고, 그래서 비교가 공정하다.

| | A안 「렌더 그대로」 | B안 「납작한 그림체」 |
|---|---|---|
| 음영 | 연속(EEVEE 그대로) | **3단 포스터화** 0.32 / 0.66 / 0.93 |
| 선 | Freestyle 1.3px(`#1a1714`) | 안쪽 선 1px 굵힘 + `v<0.16` 을 0.06 으로 눌러 또렷하게 |
| 외곽선 | 없음 | **4px 어두운 링**(`#120e0b`), 알파 1.0 |
| 채도 | 렌더 그대로 | **무릎 곡선** s′ = 1−(1−s)^2.1, 상승분 상한 0.50 |
| 톤 | 현재 `cook_dl_a.png` 계열 유지 | 채도·명암 대비 상승 |

### 2-1. B안 파라미터는 감이 아니라 측정에서 나왔다
`art_raw/chars_front/*/Idle_0.png` 의 히스토그램을 재 봤다.

```
scholar  v평균 0.53  s평균 0.12  s(p90) 0.15
medic    v평균 0.58  s평균 0.15  s(p90) 0.33
cook     v평균 0.65  s평균 0.15  s(p90) 0.45
scout    v평균 0.50  s평균 0.12  s(p90) 0.17
```
**3D 렌더는 원래 거의 무채색이다.** 단순 배율(×1.55)로는 학자의 자주(`#6b5a7a`, s=0.26)가 회색으로 남는다.
그래서 배율이 아니라 무릎 곡선을 썼다 — 낮은 채도를 크게 들어 올리되 포화하지 않는다.
다만 그대로 두면 창백한 피부(`#efd9c8`, s≈0.16)까지 타서 C2(창백함)가 깨지므로 **상승분을 0.50 으로 잘랐다.**

### 2-2. 왜 "어두운 외곽선 + 올린 명부" 둘 다인가 (근거는 배경 렌더다)
`static/art/deep/section_hero.png` 에서 방 안 색을 직접 샘플링했다.

```
방 뒷벽  #e4ce9a (v 0.89)   ← 밝다
방 바닥  #5f5953 (v 0.37)
어두운 구석 #1a180d (v 0.10) ← 어둡다
물       #092838 / #1f5d6c
```
**한 인물의 머리·상반신은 밝은 뒷벽 위에, 다리·발은 어두운 바닥 위에 동시에 놓인다.**
그래서 밝은 쪽은 **어두운 외곽선**이 끊고, 어두운 쪽은 **올린 명부(0.93)** 가 띄운다. 한쪽만 손보면 반드시 다른 쪽에서 묻힌다.
이것은 REF_CROSS_SECTION §1-3(두꺼운 검은 테두리 = 가장 중요한 가독성 장치)을 **방 단위에서 인물 단위로 내려 적용한 것**이고, §1-6(밝은 옷으로 실루엣이 방 배경에서 떨어진다)의 우리 쪽 구현이다.

## 4. ★ 이번에 발견한 것 — 정면 단면은 깊이 방향 동작을 읽지 못한다

`PickUp` 을 0~100%로 뽑으면 캐릭터가 **카메라 쪽으로 완전히 접히면서 얼굴이 사라지고 등짐만 남은 덩어리**가 된다.

**폴아웃 셸터 주민이 늘 좌우로만 움직이는 이유가 이것이다.**

- 이번 조치: 읽히는 구간(0~22%, "아래로 손을 뻗는다")만 3번째 행으로 쓴다.
- 증거는 지우지 않고 페이지 §5에 **실패 컷**으로 남겼다(`static/art/chars/front/blob/*`). 이 제약을 다음 사람이 다시 발견하지 않도록.
- 함께 확인한 것: `Run`·`SitDown` 후반은 정면에서 잘 읽힌다. **1막 거점의 일하는 동작은 좌우·상하로 새로 설계해야 한다**(팔 옆으로 뻗기, 쭈그려 앉기, 옆으로 옮기기). → `docs/TASKS.md` 요청함에 등재.

## 6. 추천 — **B안 「납작한 그림체」**

### 왜
1. **70px 밝은 벽에서 A안은 4역할이 녹는다. B안은 8역할이 전부 남는다.** 다른 어떤 장점도 이걸 못 이긴다.
2. **단면 화면은 한 인물을 두 개의 정반대 대비 환경에 동시에 올린다**(벽 v 0.89 / 바닥 v 0.10). B안에는 그 둘을 각각 담당하는 장치가 있고(어두운 외곽선 / 올린 명부), A안에는 둘 다 없다.
3. **화면 문법의 일관성.** 단면 거점은 이미 "두꺼운 검은 테두리로 방을 끊는" 문법이다(REF §1-3). 인물만 부드러운 3D 톤이면 인물이 배경 장르와 다른 그림이 된다.
4. **"덜 만든 3D"로 보이지 않는다.** 렌더 그대로는 완성도가 낮아 보이고, 납작하게 밀면 **의도된 그림체**로 보인다. 절차 생성물의 인상 관리(07 §1의 비대칭)에도 유리하다.
5. **비용이 같다.** 같은 렌더에 후처리 30줄. A안을 버리는 것도 아니다 — 아이소(2·3막 바깥)에서는 A안 톤이 그대로 맞다.

### ★ 중요 — B안을 고르는 것이 "2D로 간다"는 뜻은 아니다
B안의 후처리는 **툰 셰이더가 실시간에서 할 일을 미리 보여 준 것**이다(음영 단계화 + 외곽선 + 채도 상승은 전부 셰이더로 가능하다).
따라서 갈래는 셋이고, 이 페이지는 세 갈래 모두에 쓰인다.

| 갈래 | 내용 | 장점 | 비용 |
|---|---|---|---|
| **2D 스프라이트 + B 톤** | 지금 시트를 그대로 씀 | 모바일에서 가장 가볍고, 프레임이 정확히 통제됨 | 방위·포즈가 늘 때마다 재렌더. 각인 조합이 파일 수를 곱한다 |
| **실시간 3D + B 톤 셰이더** | 정면 직교 카메라 + 툰 셰이더 | 각인 토글·부족 의상·포즈가 전부 런타임. 파일 1벌 | 셰이더 작업과 모바일 드로우콜 |
| **하이브리드** | 배경·먼 인물은 스프라이트, 주인공·각인 대상은 3D | 좋은 절충 | 두 파이프라인 유지 |

**캐릭터 담당 의견**: 그림체는 **B**로 확정하되, 2D/3D는 방위 수요(뒷모습·측면이 필요한가)를 보고 정하는 것이 맞다. 각인 조합이 8종·최대 3개 동시 = 93가지이므로, **각인이 화면에서 중요해질수록 3D + 툰 셰이더가 유리해진다.**

### B안의 약점(솔직하게)
- **어두운 구석(`#1a180d`)에서는 외곽선이 배경에 먹힌다.** 몸통 명부로 버티지만 방 조명 설계로 보완해야 한다(배경에 요청함).
- **포스터화가 얼굴의 미묘한 음영을 지워 8역할의 얼굴이 더 비슷해 보인다.** 구분은 모자·소품·옷 색이 담당한다.
- **정찰병 ↔ 농부**가 둘 다 올리브다(70px에서 가장 가까운 쌍).
- **요리사와 의무병이 둘 다 크림색이 지배적**이다. `data/roles.json` 에서 요리사는 body `#E0813A`(주황)인데 `ROLE_DEF` 의 `Clothes` 가 `$accent`(크림)에 걸려 있어 상의가 크림이다. 바지·모자띠만 주황이라 구분은 되지만, 상의를 `$body` 로 바꾸면 훨씬 강해진다 — **정식 8역할 외형 변경이라 이번 비교에서는 손대지 않았다.** PM 판단 요청.
- 4px 외곽선은 256px 원본에서 다소 두껍다. 스프라이트를 128px로 낮추면 자동으로 해결된다.

## 7. 04 §5 자가 검수 5문항

1. **검은 실루엣으로도 8역할이 갈리는가?**
   **B안은 갈린다**(70px·3배경 전부). A안은 밝은 벽에서 4역할이 탈락한다. 가장 가까운 쌍은 정찰병↔농부(올리브)이고 밀짚모자 챙으로 갈린다. S1의 시그니처(등짐·높은 모자·붉은 십자·시안 고글·넓은 밀짚모자·가슴의 책·챙 넓은 모자·작은 키)가 정면에서도 전부 살아 있다.
2. **큰 눈·창백함·부족 적응이 보이는가?**
   보인다. 정면이라 아이소보다 **더** 잘 보인다(아이소에서는 눈이 비스듬했다). B안은 채도 상승 상한 0.50으로 피부가 타지 않게 잘라 창백함을 지켰다 — 이 상한이 없으면 얼굴이 주황이 되어 C2가 깨진다.
3. **각인 3개가 겹쳐도 읽히는가?**
   **176px에서는 읽힌다**(목의 이빨 끈 · 허리 가죽띠 · 오른뺨 흉터가 서로 다른 높이). **70px에서는 허리띠만 남는다** — 미완이다(§8-4). 각인을 작은 화면에서 보여주려면 색 대비를 주거나 별도의 아이콘 배지가 필요하다.
4. **짐승이 사람보다 가깝고 따뜻해 보이는가?**
   **이번 범위에서 판정 불가.** 짐승·공룡의 정면 스프라이트를 만들지 않았다(지시 범위가 8역할). S2에서 확인한 성질(개 Idle의 기대는 포즈, 짐승만 밝은 눈)은 3D에 그대로 남아 있다. 정면 스프라이트로 가기로 결정되면 같은 스크립트에 `animals`/`dinos` 를 붙이는 데 한 시간이면 된다.
5. **발 원점·키·+Z·클립이 맞는가?**
   맞는다. 발 기준선 240px 고정, 실측 키 8개가 S2와 소수점 4자리까지 동일(회귀 0), 클립 3종(GLB의 7종 클립은 손대지 않음). `+Z 정면`은 2D 산출물이라 방위 0°(정면)로 대응한다.

## 8. 미완·리스크

1. **정면 한 방위뿐이다.** 단면 화면에서 사람이 벽을 보고 일하면 뒷모습이 필요하고, 좌우로 걸으면 측면이 필요하다. 지금은 Walk도 정면 제자리걸음이다. 2D로 간다면 **정면·뒷면·측면 3방위 × 8역할**이 최소 물량이다(현재의 3배).
2. **일하는 모션이 온전하지 않다**(§4). 좌우·상하 동작으로 새로 만들어야 한다.
3. **용량 5.5MB**(A안 8시트 + B안 8시트 + 부속). 채택 후 한쪽만 남기면 약 2.5MB, 프레임을 5→3으로 줄이고 PNG 팔레트화하면 1MB 이하로 내려간다. 지금은 **비교가 목적이라 둘 다 남겨 뒀다.**
4. **각인이 70px에서 안 읽힌다**(§7-3).
5. **어두운 방에서 외곽선이 먹힌다**(§6 약점). 배경 쪽 명도 설계와 함께 풀어야 한다.
6. **짐승·공룡 정면 스프라이트 없음.**
7. **부족 의상 파츠 미적용**(C3). 8역할은 있지만 일곱 부족의 적응 묘사는 아직 3D에도 없다 — S2부터의 잔여 과제.
8. **Playwright MCP 미사용.** 다른 에이전트가 브라우저를 점유해 헤드리스 Edge로 대체했다(TEAM.md §5 허용). PM 재현 시 Playwright로 한 번 더 열어 주시면 좋겠다.
